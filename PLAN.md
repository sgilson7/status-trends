# Plan

Stage 2, written by the agent from `BRIEF.md`. `B2 Require step-by-step justification`.

The plan is approved in advance (brief, Autonomy). Decisions in build order.

| # | Decision | Reason | Test that shows it holds |
| --- | --- | --- | --- |
| 1 | Data enters only as text the person gives the page: a file chosen or dropped, or pasted text. The page reads it with `File.text()` and hands the string to the core. | Jira can export CSV without any connection from this tool to Jira. A live Jira connection would need a token and a request to another origin, which the brief forbids. "Real time" means the dashboard redraws as soon as a file is opened or a setting changes. | browser check opens a sample file through the file input |
| 2 | The core parses CSV itself (RFC 4180: quotes, doubled quotes, line breaks inside quotes, CRLF, a byte-order mark) and detects comma, semicolon or tab. | No CSV crate is on the allowlist, and Jira exports carry line breaks inside quoted descriptions. | `csv.rs` unit tests |
| 3 | Dates: ISO `2026-10-12[ 13:13]`, Jira's default `12/Oct/26 1:13 PM`, `12 Oct 2026`, and numeric `10/12/2026`. Numeric dates are month-first unless a first part above 12 shows day-first, and the person can force either. Times are dropped; the day is the unit. | These are the formats Jira and spreadsheets write. A day is enough for monthly reporting and keeps arithmetic in integers. | `date.rs` tests with hand-worked day numbers |
| 4 | Column roles are guessed from header names: created, status, resolved, due date, and a group column. The person can change each one in the page. | Exports differ per site; a wrong guess must be one click to fix. | `columns.rs` tests on Jira and class headers |
| 5 | Each distinct status goes into one of four groups: still requested, pending, completed, excluded (won't do, duplicate). The guess uses keywords; the person can change any status's group. | The request names "still requested, still pending versus completed". Excluded items should not count against completion. | `status.rs` tests |
| 6 | Periods: year, quarter or month, with a fiscal year starting in any month. A fiscal year is named for the calendar year it ends in (FY26 = Oct 2025 to Sep 2026 with an October start). | Many organisations report on a fiscal year that does not start in January. | `period.rs` tests |
| 7 | The "as of" day is the latest date in the file unless the person types one. The core reads no clock. | A clock in the core would make the same file give different answers on different days, and the tests would drift. | `analysis.rs` tests |
| 8 | Per period: items created, split by current status group; items completed (resolved in the period); completion rate of the items created in the period; open at the end of the period; median days to complete. Changes are whole percents, rounded half away from zero, against the previous period and the same period a year before. The period holding the as-of day is marked *in progress* and comparisons use the last complete period. | These are the counts the request names, and a part period compared with a full one shows a fall that is not real. | hand-computed cases in `tests/hand_computed.rs` |
| 9 | Insights and risks are rules in the core, each with a severity (risk, watch, good, note), an icon and a sentence. Thresholds are settings: completion target (80%), growth alert (20%), open too long (90 days). | The request asks the tool to "identify risks"; a rule that is in the core can be tested and explained. | `insights.rs` tests, one per rule, each watched failing |
| 10 | Charts are drawn by the core as lists of SVG shapes in integer view-box coordinates, with class names for colour and a tooltip per hit area. The page creates the elements and does nothing else. | Builder's page holds no number and no arithmetic (D3), and a chart's geometry is a rule worth testing. | `chart.rs` tests; boundary test on the page |
| 11 | Charts: created per period by status (stacked, with the % change over each column); created vs completed (lines); completion rate with the target line; open at period end; year over year (one line per year across quarters or months). Every chart has the table view beside it. | Follows the data-visualisation method: one axis per chart, legend for two or more series, no colour-only identity, table view. | browser check reads the chart titles and table |
| 12 | Group breakdown table and a "show only this group" filter. | Lets a manager look at one team and a teacher at one student. | `analysis.rs` tests |
| 13 | Two vocabularies from `data/strings.json`: requests (Jira) and a class (students and assignments). Two invented sample files, generated by a seeded script. | The request asks that the tool transfer to teachers. | browser check loads both samples |
| 14 | Exports made in the page: the period table as CSV, a chart as SVG, and printing. Each is a Blob saved to the person's own device. | Reporting needs the numbers outside the tool, and the person chooses where they go. | browser check saves the CSV |
| 15 | Privacy: CSP `connect-src 'self'`, `form-action 'none'`, `referrer` `no-referrer`; every file the page needs is fetched before it reports ready, so **no request of any kind** happens afterwards; no browser storage; no third-party anything. | The brief puts privacy above everything. Fetching all of the page's own files up front makes "nothing is requested after load" a checkable statement and lets the page work offline once open. | browser check fails on any request after ready, any storage, any CSP violation; `no_storage.rs` |
| 16 | Title art drawn as TikZ by `tools/art.py`, compiled with pdflatex and pdftocairo to PNG, in the look of the other tools' title art. No text in the art. | The brief's art instruction. | `tools/art.py` checks size and the absence of text commands |
